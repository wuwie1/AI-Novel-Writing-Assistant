# 小说助手上游同步

以用户当前工作区为目标。先读目标仓库的 `AGENTS.md` 和 `docs/wiki/architecture/server-deployment.md`。在这个工作区获取 `git symbolic-ref --quiet HEAD` 和起始提交。当前检出的本地分支是本轮唯一的整合和推送目标。上游来源是 ExplosiveCoderflome 原仓库的远端默认分支；fork 为 wuwie1，两者仓库名均为 AI-Novel-Writing-Assistant。detached HEAD 无法确定目标分支时说明原因并停止，不自行切换、创建或更新其他本地分支。

## 指令范围

- **检查上游更新**：只运行本技能的 `scripts/check-upstream.sh`，传入目标工作区路径。汇报当前分支与上游默认分支、fork 同名分支的差距。此步不合并、推送或部署。
- **同步上游**：将上游提交合入当前分支并验证。保持在原工作区和分支，不自动推送。
- **同步上游并部署**：完成本地同步和校验，只推送当前分支到 fork 的同名分支，再将同一提交部署到服务器并验收。用户限定只检查、只本地同步或不推送等范围时，按其要求执行。
- **服务器更新**：使用当前分支的本地 HEAD 执行服务器更新，包含重启 API 和网页服务。可部署尚未推送的提交。
- 单独补推或补部署也使用当前分支。上游无新提交时按用户请求核对 fork 或实际部署版本。补部署若版本、清单和服务健康均已对齐，汇报已对齐即可；明确要求重启或执行“服务器更新”时仍须重启验收。

## 检查与合并

从本技能所在目录定位 `scripts/check-upstream.sh`。脚本核实两个远端，查询上游公布的默认分支并抓取该引用。fork 只比较当前分支的同名引用；远端尚无该分支时可继续检查上游。抓取或查询失败时报告失败。新克隆缺少 `upstream` 时，按目标仓库 `skill_tools.md` 核实 `origin` 后配置原项目；替换已有远端遵循仓库 wiki 的备份规则。

固定脚本报告的本地、上游和 fork SHA，检查完整差集。若 fork 同名分支有独有提交，先纳入当前分支，再直接合入上游 SHA。工作区干净且历史可快进时直接快进。遇到分叉或工作区有未提交改动时，从本轮起始提交建立 detached 临时 worktree，在那里整合并验证，保留已有提交、暂存区与用户文件。将结果带回原分支前重新核对分支和起始 SHA，用同一条安全快进命令 `git merge --ff-only --no-autostash --no-overwrite-ignore <已验证提交>` 更新原工作区。若 Git 因本地修改而拒绝快进，保留原工作区与隔离结果，报告路径、SHA 和阻挡文件，暂停后续推送与部署。不自动暂存、提交、清理或覆盖用户改动。

同时审查文本冲突和双方改过但 Git 自动合并的文件。既有交叉点包括拆章预算、角色目录、Prompt 版本、注册器与回归用例。使用目标仓库的 `.agents/skills/readme-release-updater/SKILL.md` 核对提交或推送范围。README 仅保留最新日期，完整发布历史与有长期价值的 wiki 规则保留双方内容。

## 校验与推送

检查起始提交、固定的上游 SHA 和既有 fork 同名分支提交都是合并结果的祖先。按本轮差异构建和回归；交叉修改同时运行上游与 fork 相关用例，记录通过、失败、跳过数。核对验证的 tree 与最终提交一致。共享包、前后端输入及工具链均相同时才复用检查。使用隔离测试库；UI 交互验收遵循仓库规则。

仅在授权推送时复核 `origin` 所有 push URL。复核当前分支与已验证提交，使用单一明确的 refspec 将该 SHA 推送到 `refs/heads/<当前分支>`，并回读 fork 同名引用确认。拒绝非快进时重新抓取、整合、验证；不强推。

## 部署

遵循目标工作区的 `infra/server/README.md`。从 `desktop_mac/config/app.example.json` 和本机配置核对主机、账户与目录。使用 SSH 别名时以 `ssh -G` 核对目标，使用 BatchMode=yes 和 ClearAllForwardings=yes。核实服务器仓库、当前发布分支、部署清单、服务、空间及工作区。服务器分支与本地不一致或服务器有本地修改时报告现场，保留服务器原状。若当前工作区使用旧版部署入口，只接受具体的 `origin/<分支名>`，从已核对的当前分支动态生成该引用，预演和正式部署使用同一值。

1. 核对当前分支、干净工作区和候选 HEAD。未提交的内容不进入部署；有改动时列出需处理文件。同步后部署时，候选须与已验证并按请求推送的 SHA 一致。
2. 执行 `make server_update DEPLOY_REF=current DRY_RUN=1`，让部署入口以当前检出的分支解析发布引用。核对 `inspection` 的服务器基线 `current` 和本次 `candidate`。用户只要求预演时，到此报告结果。
3. 复核当前分支及候选仍与预演一致，执行 `make server_update DEPLOY_REF=current`。读取 `deployment_plan`，版本相同时重启，新版本按受影响输入构建。已有对应 SHA 与发布分支的真实 CI 或本机构建与测试记录，可传入 `DEPLOY_VALIDATION_FILE`。服务器在隔离目录构建，使用临时数据库测试。迁移、依赖或环境差异必须重新核验。
4. 部署事务须先用 SQLite backup API 创建一致快照并核验 integrity_check，校验资产、配置及可回退的旧构建，记录备份目录。破坏性数据操作须满足 AGENTS.md 的批准和验证要求。
5. 核对成功的 `deployed` 回执、SHA、部署清单和备份路径。验收 API、网页静态资源及已有的本机隧道入口。失败时报告具体阶段和日志路径，核对源码、产物、清单和回滚状态。性能对比取本批 `timings.json`。
